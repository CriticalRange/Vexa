# Megabonk x87 reduced-precision experiment

The FEX 2610 candidate implements `X87ReducedPrecision`; default is false. To support a selective launch experiment, VEXA now explicitly mirrors the `FEX_X87REDUCEDPRECISION` launch variable into the host process before FEX loads its environment configuration. It is cleared at subsequent launches unless explicitly supplied. No global FEX default was changed.

The candidate debug APK SHA-256 was `bb9d846028c649ec11f772ceb118ba6825d914bc556f09518fed970677d7b8a1`. Build passed with the pre-existing old FEX verification/staging steps skipped; the FEX merge remains uncommitted. Android installation succeeded. Megabonk was started through GameActivity with `FEX_X87REDUCEDPRECISION=1`, `VEXA_FEX_DISKCACHE=1`, `VEXA_FRAME_STATS=1`, and `VEXA_FEX_DIAGNOSTICS=1`. Actual running FEX log reported `x87Reduced=true`, and installed payload mismatches were zero. The option changes code generation, and FEX selected a different disk cache database than the prior default-x87 launch.

The game reached the menu and an actual gameplay scene. In one screenshot the in-game overlay reported 56 FPS, but there was no controlled same-scene A/B, and the existing frame probes did not capture this game's presentation path. No claim of an FPS gain or loss is supported. FEX logs contained handled signal fixups, not proof of an unhandled crash. The game was paused after a short run; no obvious visual corruption was identified in the screenshots, but visual, numeric, physics, audio, and long-run correctness are not established. Lower x87 precision can change results and cause rendering bugs; do not make it global without title-specific validation.
