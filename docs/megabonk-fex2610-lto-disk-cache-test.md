# Megabonk: FEX 2610 ThinLTO and disk cache test

On 2026-10-29 the candidate debug APK was built with the FEX 2610 merge candidate, Android FEX allocator, FEX ThinLTO and VEXA ThinLTO. CMake 3.22 Android IPO now uses NDK lld in place of unavailable gold when IPO is requested. `VEXA_LTO=ON` selects IPO for the VEXA Gradle build; the selected FEX build must separately have LTO enabled. The debug VEXA build did not have an explicit optimized build type, so this experiment must not be used to establish an LTO FPS gain. The build skipped the old incompatible FEX verification/staging tasks and used previously staged candidate host/guest thunk pairs. The FEX merge remains uncommitted.

Installed APK SHA-256: `d806c747d1cb42d39183adaff6e1e52e50e56b2039ef8ead0e4ec3efe9d2c6e6`. Packaged and actual device-loaded `libvexa.so` SHA-256: `d7dab6d4baf84e771baf893fc5065778567bbdd534fed834a6dff3fd0e56ff13`. Megabonk was launched through GameActivity with `VEXA_FEX_DISKCACHE=1` using its normal GL preset. The runtime logged cache enabled, mapped the private FOZ cache in process maps, and reached both main menu and actual gameplay. A gameplay screenshot showed the in-game FPS overlay at 63 FPS at one instant; this is not a benchmark. The character died shortly thereafter. Handled signal fixups appeared in the logs; no unhandled crash was observed in this short test.

At first exit the cache database was about 142 MiB with an approximately 12 MiB index. The game was force-stopped after the death screen and restarted once with the same cache; the second run mapped the same cache file and reached the main menu. This does not prove a cache hit rate, startup improvement, gameplay stability, or FPS improvement. The application was left at the main menu. The run included Steam trace logging. No matched baseline, p50/p95/p99 measurement, thermal control, or long-run testing was performed.
