## Android allocator and syscall follow-up

- Android's FEX allocator initializes rpmalloc once before its first FEX-owned allocation, using the actual system page size and stable bionic mmap/munmap callbacks. FEX's separate guest-address mappings retain their existing hooks and 32-bit guest allocator. This deliberately avoids routing old rpmalloc spans through a later, different mapping owner; it does not interpose on bionic/ART allocations. The optional `VEXA_FEX_ALLOCATOR` switch links rpmalloc in the VEXA candidate; a CMake check rejects a mismatch between that switch and the FEX build configuration. The candidate Gradle configuration passes the switch through, but the integrated Gradle/package path is not yet validated.
- Device standalone allocator test passed early allocation, stable backend, Bionic allocation coexistence, calloc/realloc, alignment, eight threads and cross-thread frees on the 4 KiB-page device. The Android native executable test requires 64-byte TLS alignment; this is a test executable requirement, not proof about all APK environments.
- An rpmalloc-enabled candidate `libvexa.so` loaded successfully with `RTLD_NOW` on device. Its local and device SHA-256 matched: `9cce74676f0fa45a528832d5f8f3ce373f6f81fb6f3c5826540ecc3bf8bc8510`. Using the isolated standalone loader and a separate temporary rootfs, actual FEX x86-64 and static i386 hello guests produced their expected output. This is not a graphical app or Proton game validation.
- The upstream `NeedsLoaderFD` change initially classified VEXA PE launches as ELF and was incompatible with the VEXA trampoline's path/argv contract. The candidate excludes PE and VEXA path-backed reexec from this FD handoff, preserving upstream behavior for FEXInterpreter; emulated guest `execveat` FD handoff through VEXA now fails explicitly with `ENOTSUP` pending implementation. A native x86-64 guest pathname exec/re-entry test and an unsupported-FD return test passed on device. A minimal PE fixture passed through guest exec to a native capture executable with its path/argument intact and no `FEX_EXECVEFD`. Other execve/argv, shebang, seccomp and real PE/Wine cases still need coverage.
- A real x86-64 guest verified Android SysV IPC `ENOSYS` fallbacks, compatibility-session `futex_waitv` fallback and `accept` to `accept4` redirection. A separate guest confirmed compatibility-session `/tmp` mkdir, chdir and mkdirat resolve into the temporary rootfs. These are focused tests, not full syscall/Proton coverage.
- A standalone x86-64 GL probe loaded the candidate GL host thunk, but could not create/bind a GLX context because the standalone test has no Android window. Its failure does not establish a GL implementation defect or prove graphical integration; test through the app with a real surface.

## Required before adoption

- Reconcile all nine `scripts/patches/fex-vexa-*.patch` with the merged code and update the verification method. Independent textual checks report `exec`, `proton-fs`, `android-fsync` and `android-seccomp` as conflicts; the other five reverse-apply cleanly. Current `tools/apply_fex_compat.py --check` stops at `exec`. Marker presence alone is not proof of semantic equivalence. Preserve PE/reexec, guest exit, socket, FD ownership, rootfs and Android syscall behavior and test them.
- Review the full upstream/fork overlap, especially Vulkan generator configs, Android guest/host ABI, JIT signal paths, syscall handling, SMC/cache invalidation, 32-bit allocation and host thunk lifecycle. Upstream changes that merge without conflict can still change Android behavior.
- Validate Windows host thunkgen warnings and generated custom dispatch mappings. Rebuild all host/guest thunk pairs from the same source, including 32-bit coverage, and run regression probes. The Gradle external guest build also needs validation with Windows-safe compiler paths and the new `ENABLE_FEX_ALLOCATOR` option.
- Decide allocator policy only after app-process Android 64/32-bit graphics/thunk and coexistence tests; the isolated static 64/32-bit guests and host-thread allocator test above passed on a 4 KiB device. Test 16 KiB pages where available. Do not turn it on globally merely because its object built.
- Update the VEXA FEX pin, compat checks, build options and runtime asset stamp only after the candidate merge is complete and testable. Rebuild and stage matched binaries together; verify hashes, clean install and dirty upgrade. Never mix old and new thunk pairs.
- Run native ELF and Proton/DXVK smoke tests, Vulkan and GL rendering/input/surface recreation, 32/64-bit guest tests, signal and exec/fork tests, and cold/warm game runs. Compare matched gameplay p50/p95/p99, CPU/GPU and thermal data before claiming FPS gains.
